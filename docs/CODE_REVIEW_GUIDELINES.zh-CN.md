# EvoReview 代码审查标准与流程

> 版本：v1.0（2026-11-12） · 维护人：项目维护者 · 适用范围：`evoagent/`、`scripts/`、`tests/` 及部署配置的全部变更
>
> 本标准由一次真实的审查教训直接驱动：在 702 个测试全部通过的情况下，仍通过人工审查复现出 3 个确凿的多租户越权缺陷（跨租户账号接管、代签平台管理员令牌、auto_fix 授权绕过）。**测试绿 ≠ 代码没问题**，这是本标准要解决的核心矛盾。

## 1. 审查原则

1. **机器查风格，人查逻辑。** 格式、命名风格交给自动化工具（lint/format）；人工审查聚焦机器查不了的东西：正确性、安全边界、设计取舍、可维护性。
2. **每个 PR 必须被审查，包括维护者自己的。** 自审（self-review）不豁免，只改流程（见 §5.6）。
3. **可疑即验证。** 审查中发现的疑似缺陷，能用运行时复现确认的就不停留在"看起来有问题"。
4. **审查意见对事不对人。** 每条意见说清楚"是什么问题、为什么、怎么改"，并标注严重级别。
5. **小步快跑。** 单个 PR 建议 ≤ 400 行有效变更；超过时应主动拆分，或 PR 描述中给出阅读指引。

## 2. 严重级别定义

| 级别 | 含义 | 处置规则 |
|---|---|---|
| 🔴 Blocker | 安全漏洞、数据丢失/损坏风险、越权、竞态、破坏既有契约、关键路径无错误处理 | **必须修复后才能合并**，无例外 |
| 🟡 Suggestion | 输入校验缺失、含糊命名、重复代码该抽取、重要行为无测试、明显性能问题 | 合并前应修复；确有取舍时须在 PR 中记录理由 |
| 💭 Nit | 风格不一致、命名可更好、文档缺口、可考虑的替代方案 | 可选修复；不阻塞合并 |

审查意见格式（每条意见三要素齐全）：

```
🔴 安全：SQL 注入风险
位置：stores/sqlite/store.py:42 — 用户输入直接拼进查询。
为什么：name 参数若含 ' -- 等片段会改变查询语义。
建议：改用 ? 参数绑定（本项目已有先例：store.get_user）。
```

## 3. 审查清单

按变更内容选取适用项；打勾不是目的，**逐项真正看过**才是。

### 3.1 正确性

- [ ] 边界条件：空输入、空集合、None、超长字符串、并发重复提交
- [ ] 错误路径：异常被谁处理？是否存在 `except Exception: pass` 式吞错（本项目红线：禁止裸 `except`）
- [ ] 状态机转换：新增状态是否处理了断点续跑（harness 的检查点语义）
- [ ] 资源生命周期：连接、文件句柄、临时目录是否在异常路径上也能释放

### 3.2 安全（本项目重点，见 §6 红线清单）

- [ ] 租户隔离：新查询是否都带 `tenant_id` 过滤？操作对象是否可能属于其他租户？
- [ ] 权限判定：是否在 API 入口做了权限检查？`manage` / `fix` / `platform` 权限语义是否用对？
- [ ] SQL：全部参数绑定，禁止 f-string / `%` 拼接（含动态表名、排序字段）
- [ ] 命令执行：`subprocess` 必须列表参数（禁 `shell=True`）；涉及外部仓库内容的执行必须声明隔离方案
- [ ] 外部 URL：是否经过 host 白名单（`is_github_url`）？token 是否可能发往非白名单域？
- [ ] 密钥与日志：密钥/token/密码不出现在日志、错误信息、异常文本中；比较用 `compare_digest`
- [ ] 配置变更：新增 Settings 字段是否有启动校验？不安全默认值（默认开放）是否被论证过？

### 3.3 测试

- [ ] 新行为有对应用例；**修 bug 必须先有能复现该 bug 的失败用例**（回归测试）
- [ ] 安全相关变更必须有**负向测试**：越权尝试应断言被拒绝，而非只测正常路径
- [ ] store 层变更需同时跑 SQLite 契约测试；涉及 PostgreSQL 路径的注明是否实测
- [ ] 不新增依赖外部网络的测试；确需外部服务的用 `skipUnless` 并说明

### 3.4 可维护性

- [ ] 符合 ports / adapters 分层：业务逻辑不进 `adapters/`，方言差异收敛在 `shared/`
- [ ] 无三处以上重复的同类逻辑；新魔法数字进 `config.py` 的 `Settings` 而非散落
- [ ] **新增**公开函数有类型标注与一句话 docstring 说明意图（不是复述签名）；存量代码顺手改，不要求一次补齐
- [ ] `api.py` 等已有超大文件：不鼓励继续增长，新路由尽量把业务放进 `app/` 模块
- [ ] 文档同步：README（英/中）、`openapi.py`、`.env.example` 与行为变化一致（`test_readme_toc.py` 会兜底，但别只靠它）

### 3.5 性能

- [ ] 循环内无逐条查询（N+1）；批量操作优先
- [ ] LLM 调用点：有超时、有重试上限、失败有降级路径
- [ ] 大 payload（diff、报告）有大小上限校验

## 4. 分工：自动化门禁 vs 人工审查

| 检查 | 承担方 | 说明 |
|---|---|---|
| 语法/编译 | `compileall` / CI | 合并前必须通过 |
| 全量测试 | `pytest -q`（≥ 当前基线通过数） | 用装齐依赖的解释器跑；**当前基线：732 passed / 31 skipped**（Python 3.9，Anaconda 环境），基线变化时更新此行 |
| 格式与 import 顺序 | lint（待引入 ruff，见 §9） | 自动修复后 diff 干净 |
| 架构守护 | `tests/test_architecture.py`、`test_readme_toc.py` | 分层违规、文档失同步直接红 |
| 契约一致性 | `tests/test_store_contract.py` 双后端 | store 变更必跑 |
| 逻辑正确性、安全边界、设计取舍 | **人工审查** | 本标准的核心内容 |
| 疑似缺陷确认 | 运行时复现 | 参照 §6.3 |

## 5. 审查流程

### 5.1 分支与提交

- 分支命名：`feat/…`、`fix/…`、`sec/…`（安全修复）、`chore/…`
- 提交信息：一行主题（祈使句，说明"做了什么"）+ 空行 + 正文（动机与关键取舍）；安全修复在正文列出**触发条件 → 影响 → 修复方式**
- 一个提交只做一件事；混入的无关改动先 rebase 拆出

### 5.2 提交前自检（作者义务）

1. `compileall` + 全量 `pytest` 本地通过
2. 对照 §3 清单逐项过一遍（尤其是 3.2 安全项）
3. PR 描述按 §7 模板填写；安全相关变更显式标注 `[security]`
4. AI 参与生成的代码按 §8 标注

### 5.3 PR 描述最低要求

- 改了什么（一句话）+ 为什么（动机/issue 链接）
- 影响面：动了哪些契约（API / store / 配置 / 部署行为）
- 测试证据：新增/修改了哪些用例，全量测试结果
- 部署注意：是否改变默认行为、是否需要迁移或新配置项

### 5.4 审查执行

- 审查者优先看 PR 描述里的"影响面"，再读 diff；**先读测试，再读实现**——测试能最快暴露意图偏差
- 意见一次性给全（不允许挤牙膏式分轮提交意见），每条按 §2 标注级别
- 对不确定的设计意图，先问再判，不臆测

### 5.5 意见处理与合并

- 🔴 全部解决 + 🟡 修复或记录理由 → 才可合并
- 审查者负责确认每个 🔴 的修复确实闭环（复测/复现不再触发）
- 合并方式：默认 squash 合并，保持主干历史可读
- **分歧升级**：作者与审查者对某条意见无法达成一致时，以 §10 的裁决原则决定；仍无法决定的，🟡/💭 降级为记录后合并、🔴 必须按审查者意见先修（事后可再议）

### 5.6 维护者自审流程

单人开发或紧急修复时：开 PR → 自审 → 在 PR 评论中写一段"自审记录"（重点：影响面、安全清单结果、取舍理由）→ 冷静期后（非紧急 ≥ 1 小时）再合并。安全修复（`sec/` 分支）始终要求第二双眼睛或至少一次完整的运行时复现记录；没有 PR 平台可用的热修复，复现脚本与关键输出必须落盘到 `output/` 或对应测试文件，作为审查证据留档。

## 6. 安全专项

### 6.1 红线清单（触碰即 🔴）

1. 跨租户读写：任何 store 查询/API 不得缺 `tenant_id` 约束，除非显式标注 platform 语义并校验 `platform_admin`
2. 全局资源当租户资源操作：密码、platform 标记等全局字段只能由平台权限或本人修改
3. 用户名/身份全局唯一性被绕过（如"同名即接管"类路径）
4. 令牌代签：为他人签发长期凭证必须要求平台权限
5. SQL 拼接、`shell=True`、`eval/exec`、`pickle.load` 反序列化外部数据
6. 非白名单 URL 发起带凭证请求（SSRF 面）
7. 密钥硬编码；日志/异常泄漏凭证
8. 默认开放的授权开关（fail-open）——安全相关默认值必须 fail-closed，除非在 PR 中专门论证

### 6.2 安全变更的额外义务

- PR 标题带 `[security]`；描述必须包含**攻击路径推演**：谁能触发、前提条件、影响范围
- 必须有负向回归测试（拒绝路径断言）
- 修复后做一次运行时复现确认（内存库/最小脚本），复现脚本或关键输出贴进 PR
- 同类隐患排查：修复一处权限缺陷时，grep 同类调用点，确认没有"兄弟漏洞"（本项目实践中 `/v1/auth/token` 修复后就曾牵出密码/active 端点的同类残留）

### 6.3 运行时复现方法

静态审查结论必须能被运行时验证才算确认：

```bash
# 用装齐依赖的解释器 + 内存库，构造最小攻击路径
"D:/JetBrains/Anaconda3/python.exe" - <<'PY'
from evoagent.adapters.stores.sqlite.store import TaskStore
from evoagent.adapters.auth import AuthManager, hash_password
# ...构造租户/用户，模拟攻击者的 API 调用序列，断言结果
PY
```

复现要点：使用 `:memory:` 库、不依赖网络、脚本可直接粘贴运行、输出能明确回答"绕过成功/被拒"。

### 6.4 已知部署侧风险（审查时不重复报，但要防恶化）

- `EVOAGENT_REPAIR_TEST_COMMAND` 在外部 PR 源码副本中执行测试命令，无容器隔离——部署侧须用禁网沙箱；审查相关代码改动时确认该警告文档仍在
- 配置 `TRUSTED_PROXIES` 必须同时开启 `AUTH_REQUIRED`（已有启动校验强制）

## 7. PR 描述模板

```markdown
## 变更内容
<一句话>

## 动机
<为什么改；关联 issue/讨论>

## 影响面
- API 契约：[有/无，列出端点]
- store 契约：[有/无；SQLite/PG 双后端是否都验证]
- 配置/部署行为：[有/无；新配置项或默认值变化]
- 文档同步：README / docs 是否需要更新

## 测试
- 新增用例：<列表，含负向测试>
- 全量测试：<N passed, M skipped>

## 自查（作者勾选）
- [ ] §3.2 安全清单逐项已过
- [ ] 无红线项触碰（§6.1）
- [ ] AI 生成部分已按 §8 标注
```

## 8. AI 生成代码的特别审查要求

本项目大量使用 AI 辅助编码，这不禁止，但有额外规则：

1. **披露**：PR 中说明哪些部分由 AI 生成/辅助（无需逐行，模块级即可）
2. **重点怀疑区**：AI 生成代码最常见的问题不是风格，而是——
   - 权限检查"看起来有"但条件写错（如只判了角色没判租户）
   - 异常处理吞错、失败静默降级
   - 引用了不存在或已改名的内部 API（幻觉）
   - 测试写得漂亮但只覆盖正常路径（happy path）
3. **审查者对 AI 生成部分的 🔴/🟡 不因"是 AI 写的"而放宽或加严**——标准同一把尺
4. 作者对最终代码负全部责任，"AI 写的"不构成缺陷理由

## 9. 工程化配套（待办，按优先级）

1. **引入 ruff + CI 门禁**：`pyproject.toml` 目前只有 pytest 配置；`scripts/` 已有十几处 `# noqa: E402`，说明 lint 需求客观存在。建议 ruff（含 `E/F/B/S` 规则组）+ GitHub Actions 跑 compileall + pytest + ruff
2. **补越权负向测试基线**：一组"租户 A 的 manage 用户尝试操作租户 B / platform 用户"的端到端用例，防止再次出现"测试全绿但越权存在"
3. **HTTP 契约单一数据源**：`api.py` 路由表、`openapi.py`、`tests/test_openapi.py` 三处手工同步是持续出错源，应收敛为一处生成
4. CODE_REVIEW_GUIDELINES 的规则应尽量转化为可执行检查（lint 规则、架构测试），能自动化的不要靠人记

## 10. 标准自身的维护

- 本标准每次因真实缺陷修改时，在文末追加一行变更记录：日期 + 触发缺陷的一句话描述
- 规则争议的裁决原则：**最近一次真实事故的教训优先于通用最佳实践**
- 每季度回顾一次：哪些条款从没拦住过任何问题？删掉或降级它——标准贵在可执行，不在全
