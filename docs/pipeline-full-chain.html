①

入口层：REST API 与 GitHub Webhook

evoagent/api.pyevoagent/adapters/github.pyevoagent/app/github.py

详细解释 TECHNICAL / 源码视角

链路的两个入口。API 入口接受 POST /v1/reviews 直接提交 diff（同步或 ?async=true 异步）；Webhook 入口接收 GitHub pull_request 事件，从 payload 中取 diff_url 拉取 PR diff。

  • 防伪造：每个 Webhook 必须通过 X-Hub-Signature-256 的 HMAC-SHA256 校验，比较使用 compare_digest 防时序侧信道。
  • 防重放：pull_request.updated_at 与当前时间偏差超过 EVOAGENT_WEBHOOK_MAX_AGE_SECONDS（默认 600s）直接拒绝。
  • 租户绑定：payload 带 installation.id 时必须已通过 /github/setup 绑定到租户，防止任意人把 App 安装事件投进别人的租户。
  • 幂等去重：claim_webhook(delivery_id) 保证同一次投递重复推送不会产生两个任务。
输入POST /v1/reviews 的 diff，或 POST /webhooks/github 的 payload 与 X-Hub-Signature-256 头。
输出已验签、已防重放、已绑定租户的 diff + tenant_id + principal，交给 enqueue_review()。
失败出口事件不符 → 202 ignored；secret 未配置 → 503；签名或时效不符 → 401；installation 未绑定 → PermissionError。
不变量claim_webhook(delivery_id) 幂等；外呼 URL 只有通过 is_github_url() 白名单才携带 Token。

大白话 PLAIN WORDS

把这一步想成公司前台收包裹。有人递来一份代码改动，前台先核对：寄件人是不是 GitHub、封条（签名）有没有被拆过、快递单上的时间是不是几天前的旧单（防止有人捡到旧单反复投递）、包裹上写的部门在我们登记册里存不存在。

任何一项对不上，当场退回，绝不会把包裹送进办公区。同一个人重复送同一个包裹也不怕，登记本上有编号，只收一次。

一句话 门口先验身份、验封条、验时间、认部门，验不过就不让进。

做坏了会怎样 少了验签或时间校验，别人就能伪造一个「PR 更新」把任意代码塞进来，或者重放旧事件，让系统白白跑一堆审查。

def verify_signature(secret: str, body: bytes, signature: str) -> bool:
    if not secret or not signature.startswith("sha256="):
        return False
    expected = "sha256=" + hmac.new(secret.encode("utf-8"), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)

任务编排：校验 → 配额 → 授权 → 建任务 → 入队

evoagent/app/review_lifecycle.pyevoagent/app/policies.py

详细解释 TECHNICAL / 源码视角

无论请求来自 API 还是 Webhook，最终都汇聚到 enqueue_review()。它是链路的「总闸门」，在真正开始消耗模型调用之前把所有廉价检查做完：

  • 输入校验：repository 非空且 ≤250 字符、diff 非空且 ≤ max_diff_bytes；必须是合法 unified diff 且有新增行。
  • 模式解析：RunMode.parse(mode)，默认 AGENTIC（多角色智能体）；未配置模型直接抛 ModelNotConfigured（HTTP 503）。
  • 授权链：仓库根目录白名单 → enabled_agents / enabled_skills 校验 → 租户仓库授权（grants）。
  • 建任务 + 入队：任务落库（状态 PENDING），payload 存 github_issue_url / installation_id 以便断点续跑后还能用同一套凭据回帖；然后提交队列（Redis Streams，message_id = task_id）。入队失败会把任务置 FAILED 并记录 trace。
输入repository / diff / tenant_id / mode / repository_root / enabled_agents / enabled_skills。
输出task_id、状态 PENDING、queue.submit(message_id=task_id)，指标 reviews_enqueued_total +1。
失败出口参数不合法 → 4xx；未配置模型 → 503 ModelNotConfigured；授权拒绝或入队失败 → 任务置 FAILED 并写 trace。
不变量所有廉价校验都发生在任何模型调用之前；回帖凭据随任务一起落库，便于断点续跑后仍用同一套 installation 发评论。

大白话 PLAIN WORDS

像去办事大厅叫号。工作人员不会一上来就开工，先检查表格填全没有、这个仓库是不是授权我们审、额度还够不够、模型服务有没有开机。全部通过才给你一个号码，把号码投进排队箱。

万一排队箱坏了，也会把这张单子标成「失败」并记一笔，不会悄悄丢掉，让你永远等不到结果。

一句话 先把便宜的检查全做完，再发号排队，绝不先花钱叫模型。

做坏了会怎样 顺序反过来会为无效请求、越权请求白烧模型费用；入队失败不记账，任务就会变成永远查不到的「幽灵单」。

def enqueue_review(self, repository, diff, pull_request=None, source="api",
                   github_issue_url="", installation_id=None,
                   tenant_id="default", mode="", repository_root="",
                   enabled_agents=None, enabled_skills=None):
    self.policy.validate_review(repository, diff)
    selected_mode = RunMode.parse(mode) if mode else RunMode.AGENTIC
    self.policy.require_agentic_model(self.chat_client_provider())
    repository_root = self.policy.resolve_repository_root(repository, repository_root, tenant_id)
    self.policy.validate_enabled_agents(enabled_agents)
    self.policy.validate_enabled_skills(enabled_skills, tenant_id)
    self.policy.authorize_repository(tenant_id, repository)
    task_id = self.create_task(repository, diff, pull_request, source, tenant_id,
                               repository_root, enabled_agents, enabled_skills,
                               selected_mode.value)
    # 持久化投递元数据：续跑的任务要用同一套 installation 凭据回帖
    self.store.update_task_input(task_id, {
        "github_issue_url": github_issue_url,
        "installation_id": installation_id,
    })
    self.queue.submit({
        "task_id": task_id, "repository": repository,
        "pull_request": pull_request, "github_issue_url": github_issue_url,
        "installation_id": installation_id, "tenant_id": tenant_id,
    }, message_id=task_id)
    self.metrics.inc("reviews_enqueued_total")
    return {"task_id": task_id, "state": "PENDING", "queue": self.queue.backend}

运行时状态机：PLANNING → EXECUTING → REVIEWING → SUCCESS

evoagent/agent/harness.pyevoagent/domain/models.py

详细解释 TECHNICAL / 源码视角

队列消费者取出任务后，ReviewHarness 用一个显式状态机驱动审查。每次状态迁移都受 ALLOWED 转移表约束，非法迁移直接报错——这保证任务永远不会「跳步」。

  • PLANNING：parse_unified_diff() 把 diff 解析成 ParsedDiff（文件列表 + 逐行新增内容）。没有新增行直接判失败。
  • EXECUTING：调用 reviewer 的 review_with_context()，跑完整条多角色链（④-⑧）。
  • REVIEWING：汇总 finding、计算风险等级、装配 ReviewReport（含 collaboration / run_mode / components / execution 元数据）。
  • 断点续跑：每步都写 checkpoint + trace；LeadSession 按 phase（scanned → delegated → workers-completed → …）持久化，进程崩溃后 POST /v1/tasks/{id}/resume 能从上一个完成阶段继续，已完成的模型调用不重跑。
输入队列 claim(task_id) 拿到的任务快照：diff / repository / tenant_id / 检查点。
输出每个阶段的 state + checkpoint + TraceEvent，最终产出 ReviewReport 并置 SUCCESS。
失败出口diff 没有有效新增行 → FAILED；ALLOWED 转移表之外的跃迁 → RuntimeError。
不变量PLANNING → EXECUTING → REVIEWING → SUCCESS 不跳步；/resume 按 phase 续跑，已完成的模型调用不重跑。

大白话 PLAIN WORDS

像流水线上的工位牌：一个任务只能按「待办 → 备料 → 施工 → 验收」的顺序挪牌，不能从备料直接跳到已完工。每做完一步就拍张照片（检查点）存好。

万一中途停电，来电后照着照片从断掉的那一步接着做，前面做过的活不用重来，也不会重复扣模型调用的钱。

一句话 按顺序搬牌子，每步留快照，断了能接着干。

做坏了会怎样 允许跳步会出现「还没审完却显示成功」；没有检查点则重启后整条链重跑一遍，成本翻倍还可能重复发评论。

def _planning(self, state):
    parsed = parse_unified_diff(state["diff"])
    if not parsed.files and not parsed.added_lines:
        raise ValueError("diff does not contain a valid unified diff with added lines")
    self._transition(TaskState.PLANNING, "Input accepted; preparing review plan")
    return {"parsed": self._serialize_parsed(parsed)}

def _executing(self, state):
    parsed = self._deserialize_parsed(state["parsed"])
    self._transition(TaskState.EXECUTING, "Reviewing %d changed files" % len(parsed.files))
    findings = self.reviewer.review_with_context(
        state["task_id"], state["diff"], parsed,
        repository=state["repository"], tenant_id=state.get("tenant_id", "default"),
    )
    return {"findings": [item.to_dict() for item in findings]}

def _reviewing(self, state):
    parsed = self._deserialize_parsed(state["parsed"])
    findings = [self._finding_from_dict(item) for item in state["findings"]]
    self._transition(TaskState.REVIEWING, "Validating and ranking %d findings" % len(findings))
    risk = self._risk(findings)
    report = ReviewReport(
        repository=state["repository"], pull_request=state.get("pull_request"),
        summary=self._summary(findings, len(parsed.files), risk), risk=risk,
        findings=findings, files_reviewed=parsed.files, reviewer=self.reviewer.name,
        collaboration=collaboration, run_mode=run_mode,
        components=components, execution=execution,
    )
    return {"report": report.to_dict()}

def _transition(self, target, message):
    if target not in ALLOWED.get(self._ctx.state, set()):
        raise RuntimeError("invalid state transition: %s -> %s" % (
            self._ctx.state.value, target.value))
    self._ctx.step += 1
    self._ctx.state = target
    self.store.transition(self._ctx.task_id,
        TraceEvent(self._ctx.step, target, message, utc_now()))

上下文准备：规则扫描 · 记忆召回 · Agent Skills · 工具套件

evoagent/agent/reviewer.pyevoagent/agent/scanning.pyevoagent/agent/memory.pyevoagent/evaluation/skills.py

详细解释 TECHNICAL / 源码视角

智能体开工前，先为整条链准备「弹药」。这一步在 _review_with_context() 里完成，产物会被 Lead 和所有 Worker 共享：

  • 规则扫描器：内置确定性扫描（本地规则 + 声明式规则），另可按租户挂载自定义扫描器；产出的规则 findings 会作为 Lead 分派的参考输入。
  • 记忆召回：memory_manager.recall() 按租户 + 仓库检索历史审查沉淀（如「该文件上次出现过 XX 问题」），失败静默降级为空并记录 ledger，不阻塞主链路。召回结果明确标注 「untrusted historical hints」——历史记忆必须用当前 diff 或工具复核。
  • Agent Skills：按租户加载技能目录（含 catalog_entry() 元数据）；请求了未注册的 skill 直接报错。资源读取用 realpath 防 symlink 逃逸。
  • 工具套件：RepositoryToolSuite 绑定仓库本地检出（可选）、AST 分析、semgrep/bandit/eslint/typecheck 等只读工具，以及可选的仓库测试命令——它们产出的「证据」稍后是过门禁的硬通货。
输入task_id / diff / ParsedDiff / tenant_id / requested skills。
输出scanners、memory_context、available_skills、RepositoryToolSuite、ExecutionLedger，一并交给 _agentic()。
失败出口请求未注册 skill → ValueError；记忆召回失败静默降级为空并写 ledger；read_resource() 用 realpath 拒绝 symlink 逃逸。
不变量记忆只标为 untrusted historical hints，必须用当前 diff 或工具复核；工具只读；每次模型/工具调用都进账本，最终写进报告的 execution。

大白话 PLAIN WORDS

工人上岗前先发资料袋和工具箱：一份不用动脑的查错清单（规则扫描）、过去审过这个仓库的笔记本（只当线索，不能当结论）、可选的技能手册，以及一堆只读工具（看文件、看语法树、跑静态扫描）。同时发一本账本，谁调用了什么、花了多少都记上。

如果 AI 想借一本库房里根本没有的手册，直接拒绝，不许它自己编一本出来。

一句话 先把资料、工具和账本摆齐，再让智能体开工。

做坏了会怎样 历史笔记被当成事实会污染这次判断；工具不设只读边界，AI 就可能改到仓库里的真实文件。

Lead 分派：一次模型调用决定「谁审什么、风险多高」

evoagent/agent/orchestration.pyevoagent/agent/lead.pyevoagent/agent/lead_session.py

详细解释 TECHNICAL / 源码视角

Lead Agent 先做一次 delegate 调用：拿到 diff、变更文件、规则扫描结果、记忆和可用 Skills 目录后，输出结构化的 delegations（每个 Worker 一个任务书：目标 objective、聚焦文件、建议 skills）和一个 risk_level（low / high）。

  • 风险分级驱动预算：高风险任务 Worker 最多 3 步工具、开放完整工具权限（可读仓库上下文）；普通任务默认只读工具或禁用工具，成本可控。
  • 可恢复：delegation 结果持久化在 LeadSession（phase=delegated），崩溃续跑时不会重复分派。
  • 归一化：normalize_delegations() 会把模型输出约束到合法 Worker 角色与真实文件列表上，防止幻觉出的任务书。
输入model_diff + changed_files + enabled_workers + skills catalog + scanner_findings + recalled_memory。
输出normalize_delegations() 后的作业单、normalize_risk_level()，以及 phase=delegated 的 LeadSession。
失败出口模型输出里的非法角色 / 文件 / skill 被归一化剔除；本次调用固定 max_steps=1、allow_tools=False。
不变量一次 delegate 调用定分工；只有 risk_level=high 才开放完整工具与 3 步预算；续跑不重复分派。

大白话 PLAIN WORDS

像工头扫一眼图纸就分工：「这块动了支付逻辑，风险高，让安全组和逻辑组各自细看，允许他们多翻资料；那边只改了文档，随便扫一眼就行。」分工结果写成作业单存档。

要是模型胡乱点了个不存在的组员或不存在的文件，归一化会把名单改回真实存在的那些，不让下游拿着空任务书白跑。

一句话 一次分工定谁审哪块、给多少预算，危险活才多给工具。

做坏了会怎样 不做归一化，编造的文件名会让审查跑偏；不做风险分级，改个 README 也会烧满工具预算。

Worker 并行审查与高风险返工：Security / Correctness-Reliability

evoagent/agent/assignments.pyevoagent/agent/bounded_role.pyevoagent/agent/orchestration.py

详细解释 TECHNICAL / 源码视角

按任务书并行运行 Worker 角色：Security（注入、凭据、越权面）与 Correctness-Reliability（逻辑缺陷、错误处理、边界条件）。每个 Worker 受「有界角色」约束：

  • 步数与工具受控：max_steps + 工具白名单；高风险才能用完整工具面，普通任务收敛为只读。
  • 证据驱动：Worker 调用 AST / 扫描器 / git 上下文等工具产生带 evidence_id 的观测记录，finding 引用这些 ID 才算「有证据」。
  • 高风险返工（revision round）：Worker 完成后，Lead 再做一次 assess-workers 评估；不满意时生成 revision_requests（附 guidance 与 required_evidence），Worker 带 Lead 反馈重跑一轮（最多 1 轮，防止无限循环）。
  • 恰好一次：revision 结果按 run_id = "1:{assignment_id}" 记账，续跑时已完成的返工不会重做。
输入delegations ×N + max_steps + tool_scope + 可用工具与技能。
输出worker_results、带 evidence_id 观测记录的候选 Finding[]。
失败出口仅 risk_level == "high" 触发 assess-workers 与最多 1 轮 revision；run_id="1:{assignment_id}" 记账防重复返工。
不变量Security / Correctness-Reliability 是「有界角色」；finding 必须引用真实存在的证据 ID 才算有证据。

大白话 PLAIN WORDS

两个审查员分头看代码：一个专盯安全（有没有把密钥写死、有没有越权），一个盯逻辑（边界条件、异常处理）。他们不能凭感觉下结论，得拿出「我在第几行看到了什么」的证据条。

工头觉得这次改动危险，会看完初稿后退回一句「证据不够，补一下」，但只补一轮，不让他们无限返工、无限花钱。

一句话 分头查、拿证据说话，危险的活儿最多退回重做一次。

做坏了会怎样 不限制工具步数，成本会失控；没有 evidence_id，后面的门禁就没法核实结论是不是真对着这行代码。

证据门禁 FindingGate：四道确定性闸，模型说了不算

evoagent/domain/gates.pyevoagent/agent/reviewer.py

详细解释 TECHNICAL / 源码视角

这是整套系统反幻觉的核心：不管 LLM 输出多「确定」，每条 finding 都要过 纯代码实现的四道闸，任何一道不过即被拒绝并记录原因：

  • Format Gate：(path, line) 必须落在 diff 真实新增行上；rule_id / title / explanation 非空。→ 杜绝「审查不存在的代码」。
  • Evidence Gate：必须有「逐字命中新增行」的证据，或合法工具证据引用，或调用链；高危 finding（critical/high）额外要求强证据工具（AST 分析、扫描器、调用链）。
  • Confidence Gate：置信度 < 0.55（minimum_confidence）拒绝。
  • Release Gate：高危 finding 必须同时给出 fix 与 test 建议，否则不发布。

被拒的 finding 不会消失——进入报告的 execution.rejected_findings（含拒绝原因），可审计、可评测误报率。

输入终审后的候选 Finding[] + ParsedDiff.added_lines。
输出GateResult(accepted, rejected, checks)；被拒项连同原因写进 execution.rejected_findings。
失败出口format / evidence / confidence(<0.55) / release 任一不过即拒绝；CRITICAL/HIGH 还需强证据工具（AST、扫描器、调用链）与 fix + test 建议。
不变量四道闸是纯代码判定，不经过模型；通过后先 redact_secret_evidence() 脱敏，才允许进入报告。

大白话 PLAIN WORDS

这是最后一道安检口，而且安检员是台不讲情面的机器，完全不听 AI 怎么解释。四道检查：你指的行号在这次改动里真的存在吗？你引用的那句代码对得上吗，说人家有高危漏洞还得拿出扫描器这种硬证据？把握有没有到及格线？说了高危却没给修法和测试建议？——那也别发。

被拦下的问题不会凭空消失，会记在「被拦下」清单里，方便以后复盘是不是拦错了、误报率有没有下降。

一句话 AI 说了不算，机器按四条硬规矩逐条查，拦下也留档。

做坏了会怎样 把判定交给模型，等于让被检查的人自己盖章；不留拒绝原因，误报率就永远没法优化。

evoagent/domain/gates.py · FindingGate.apply（:30-83）python
def apply(self, findings, parsed):
    valid_locations = {(item.path, item.line): item.content for item in parsed.added_lines}
    accepted, rejected = [], []
    counters = {"format": 0, "evidence": 0, "confidence": 0, "release": 0}
    for finding in findings:
        reasons = []
        location = (finding.path, finding.line)
        if (location not in valid_locations or not finding.rule_id.strip()
                or not finding.title.strip() or not finding.explanation.strip()):
            reasons.append("format gate: invalid location or required field")

        quoted = finding.evidence.strip()
        line = valid_locations.get(location, "").strip()
        exact_line = bool(quoted and quoted in line)          # 证据逐字命中新增行
        strong_refs = [item for item in valid_refs
                       if str(item.get("tool")) in self.STRONG_EVIDENCE_TOOLS]
        if not exact_line and not valid_refs and not finding.call_chain:
            reasons.append("evidence gate: no matching code, call chain or tool evidence")
        if finding.severity in {Severity.CRITICAL, Severity.HIGH} and not (
                strong_refs or finding.call_chain):
            reasons.append("evidence gate: high-risk finding requires "
                           "AST/scanner/call-chain evidence")
        if finding.confidence < self.minimum_confidence:
            reasons.append("confidence gate: score below %.2f" % self.minimum_confidence)
        if finding.severity in {Severity.CRITICAL, Severity.HIGH} and (
                not finding.fix.strip() or not finding.test.strip()):
            reasons.append("release gate: high-risk finding lacks fix or test guidance")

        finding.gate = {"passed": not reasons, "reasons": reasons,
                        "exact_location_evidence": exact_line,
                        "strong_evidence_count": len(strong_refs)}
        if reasons:
            rejected.append({"rule_id": finding.rule_id, "path": finding.path,
                             "line": finding.line, "reasons": reasons})
        else:
            accepted.append(finding)
    return GateResult(accepted, rejected, {
        "format": {"rejected": counters["format"]},
        "evidence": {"rejected": counters["evidence"]},
        "confidence": {"minimum": self.minimum_confidence, ...},
    })

自动修复链：授权 → LLM 出补丁 → 静态/行为双重验证 → Draft PR

详细解释 TECHNICAL / 源码视角

对已完成的 PR 任务，POST /v1/tasks/{id}/fix 触发自动修复。整条链层层 fail-closed，任何一步不达标都不会碰源分支：

  • 授权三连：任务必须是本租户的 PR 任务 → 仓库授权（grants）→ auto_fix=true 的显式 opt-in（EVOAGENT_REQUIRE_AUTO_FIX_GRANT 默认开启）；GitHub App 模式还校验 installation 归属。
  • Fix Agent 出补丁：LLM 按 unified diff 格式生成补丁，只允许改 evidence 支持的文件；应用后与原文对比，零改动直接报错。
  • 静态验证：AST/CST + compile() 编译检查，不过 → status=blocked。
  • 行为验证：必须配置 EVOAGENT_REPAIR_TEST_COMMAND——没配置时只返回 suggestion-only，不提交任何 commit、不宣称测试通过；配置了则下载源码 zip，在隔离副本上先跑基线（before）、再套补丁跑（after），对比结果不达标 → blocked。
  • 发布：全部通过后，原子 commit 到新分支 evoagent/fix-pr-{n}-*，开 Draft PR（永不直改源分支）。
输入已完成且含 PR 的 task_id + 显式 auto_fix=true grant + 归属正确的 installation。
输出status ∈ 原子提交并开 Draft PR / blocked / suggestion-only。
失败出口未授权 → PermissionError；AST/CST + compile 不过 → blocked；无 test_command → suggestion-only；before/after 行为回归 → blocked。
不变量任何一步不达标都不碰源分支；无测试命令时不提交、也不写「tests passed」；新分支 evoagent/fix-pr-* 只开 Draft PR；测试命令须在隔离沙箱执行。

大白话 PLAIN WORDS

这是「顺手帮你改」，比「帮你查」谨慎得多。先问三遍：仓库主人同意自动改了吗？改的是这个 PR 吗？GitHub 凭据确实属于本租户吗？然后 AI 写补丁，先用语法检查确认代码能编译，再把改前、改后两份代码各自在副本里跑一遍测试做对比。

没配测试命令就只把建议递给人，绝不假装「测试通过」、绝不提交。全都过了，才在新分支上开一个草稿 PR，原来的分支一根手指都不碰，合不合并不由机器人说了算。

一句话 没授权、没测试就不动代码；要动也只开草稿 PR 等人来点合并。

做坏了会怎样 跳过测试对比就提交，可能把本来能跑的代码改坏还标着「测试通过」；直接在源分支提交，等于把写生产代码的权限交给机器人。另外测试命令会执行 PR 里的代码，部署时必须放进隔离沙箱。

def create_fix(self, task_id, installation_id=None, tenant_id=None):
    task = self.store.get(task_id, tenant_id)
    if not task or not task.get("report"):
        raise ValueError("completed task not found")
    if task.get("pull_request") is None:
        raise ValueError("fix commits require a GitHub pull request task")
    self._authorize(actual_tenant, task["repository"])   # grants + auto_fix opt-in
    if resolved_installation is not None:
        owner = self.store.installation_tenant(resolved_installation)
        if owner != actual_tenant:                        # installation 必须属于本租户
            raise PermissionError("GitHub installation is not authorized for this tenant")
    client = self.github_client_for_installation(resolved_installation)
    result = self.fixer.create_fix_commits(
        client, task["repository"], task["pull_request"], task["report"],
    )
    self.metrics.inc("fix_runs_total")
    return result

详细解释 TECHNICAL / 源码视角

  • 认证与授权：JWT（HS256）+ PBKDF2 密码哈希；每次鉴权都回查用户表（禁用/移除立即生效，token 不过期也失效）；多租户 RBAC（read/review/fix/manage/audit），platform_admin 与租户 manage 分离。用户名全局唯一，防跨租户账号认领。
  • 仓库授权 Grants：按租户白名单仓库；自动修复额外要求 auto_fix=true 显式授权（默认强制，EVOAGENT_REQUIRE_AUTO_FIX_GRANT=false 可回退旧行为）。
  • 配额：每租户每日审查数 / Token / 成本上限，超限返回 429。
  • 审计：登录、建用户、改授权、修复合条、投递失败等关键动作写 audit_log，按租户隔离。
  • 可观测：OpenTelemetry span（可选）+ Prometheus 风格指标 + 失败率告警（连续失败自动评估 alert）。
  • 持久化：SQLite / PostgreSQL 双后端共享同一套方言转换 mixin（_sql() 把 ? 换 %s），业务 SQL 只写一份。
输入每个 HTTP 请求 / 每次队列消费携带的 Principal + tenant_id。
输出允许 / 403 越权 / 429 超额；audit_log、Prometheus 指标、TraceEvent、OpenTelemetry span；SQLite/PostgreSQL 或 Redis 队列落点。
失败出口越权、配额超限、JWT 对应用户已被禁用或移除（每次鉴权都回查用户表）均立即拒绝；trusted_proxies 非空且关闭认证时直接拒绝启动。
不变量用户名全局唯一；grants 按租户白名单且 auto_fix 另行 opt-in；_sql() 统一方言让双后端共用一份业务 SQL；platform_admin 与租户 manage 权限分离。

大白话 PLAIN WORDS

这些不是流水线上的某一站，而是整栋楼的规矩：进门刷卡（登录后每次还回查这人还在不在册）、每个部门只能进自己的房间（租户隔离）、每月有额度（配额）、谁在什么时候动了什么都记在监控和台账里（审计 + 指标 + 追踪）。

档案柜可以换 SQLite 或 PostgreSQL，但格子规格一样；排队箱可以用 Redis，也能临时降级成进程内的小盒子，业务代码不用改。

一句话 刷卡、分房间、限额度、记台账，十二个模块都得守这套规矩。

做坏了会怎样 任一模块绕过统一鉴权或把 tenant_id 弄丢，就会出现「看到别人家任务 / 报告」的越权；没有审计和指标，出事只能靠猜。

def authorize_auto_fix(self, tenant_id: str, repository: str) -> None:
    """Automatic repair requires an explicit per-repository ``auto_fix`` grant."""
    self.authorize_repository(tenant_id, repository)
    if not self.settings.require_auto_fix_grant:
        return
    if not self.store.has_repository_grants(tenant_id):
        raise PermissionError(
            "automatic repair requires an explicit auto_fix grant for this repository")
    if not self.store.repository_allowed(tenant_id, repository, require_auto_fix=True):
        raise PermissionError("automatic repair is not enabled for this repository")
